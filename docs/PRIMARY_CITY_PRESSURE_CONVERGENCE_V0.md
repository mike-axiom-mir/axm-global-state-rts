# Primary city-pressure convergence v0

Status: experimental host-gated city-provocation + browser-local downstream convergence rung.

## What is connected

The primary strategic convoy reaches a real aggregate city landmark, can explicitly provoke its existing city simulation, and carries that consequence through the already-existing LOCAL combat authority without creating a second city, raid, travel, or combat system.

For a local-only seat, the existing browser-local path remains unchanged. For a shared-world-bound seat, explicit remote-city provocation now first uses the already-existing hosted `city.provoke` participant command. The host normalizes attacker identity to the bound participant, applies the event to the canonical `GlobalWorldRuntime` city, and records that mutation in the existing hash-chained shared-world journal. Only after host acceptance does the browser apply its existing city-pressure follow-through. Host rejection or transport failure fails closed before browser city/pressure mutation.

The connected chain is therefore:

1. physical convoy arrival + explicit city provocation is observed by the browser strategic runtime;
2. for a bound seat, the canonical city provoke is submitted through the existing participant action budget and hosted shared-state journal first;
3. after host acceptance, the browser mirror mobilizes its existing `AggregateCity` and marks the seat's deterministic `starterDropAnchor()` as a known target in the existing `WorldPressureDirector`;
4. the director evaluates one bounded low-pressure response wave for this explicit provocation;
5. any admitted browser-local raid spends real aggregate-city defense units, food, and materials through `WorldCityFabric.dispatchRaid()`;
6. each dispatched raid keeps the director's existing great-circle `travelSeconds` and therefore has a finite arrival time at the actual LOCAL starter-drop coordinate;
7. on arrival, a bounded adapter maps aggregate raid strength into the existing `LocalCombatGameplay` contact rather than instantiating every aggregate city unit as a LOCAL Crew-equivalent;
8. the player fights that contact through the already-promoted selected-party Combat controls, including existing LOCAL casualty reconciliation and civilization-continuity consequences;
9. once the LOCAL raid contact is cleared, or the LOCAL civilization reaches terminal continuity loss, surviving aggregate strength is mapped proportionally back to the original dispatched raid and resolved through `WorldCityFabric.resolveRaid()`, returning survivors to the originating browser `AggregateCity` and recording aggregate losses there;
10. the primary strategic snapshot and threat-intel surface expose transit, arrival, bounded LOCAL admission, aggregate-city resolution, and the separate host-provocation receipt without pretending the downstream browser chain is host authority.

Repeated interaction with the same city during the same convoy visit still fails closed, so it cannot manufacture repeated scouting or raid waves. A successful bound visit keeps one deterministic host command identity for that city/journey, while the existing browser repeat guard prevents a second local consequence. Only one aggregate raid contact is admitted into a seat's LOCAL combat authority at a time; later arrivals wait rather than being silently merged into one synthetic force.

## Aggregate → LOCAL mapping contract

`aggregate-raid-local-combat.mjs` is deliberately an adapter, not an ontology claim. By default one LOCAL hostile combat packet represents up to eight aggregate raid units, with a hard cap of sixteen LOCAL combat packets per admitted raid. The ratio is an experimental bounded gameplay compression so a city-scale aggregate force does not become per-unit LOCAL simulation work. It does **not** mean one city defense unit equals one Crew, and it does not claim realism or final balance.

When LOCAL hostile packets take losses, surviving aggregate units are calculated proportionally from the original dispatched raid size and remaining combat packets. Cleared contacts resolve with zero survivors. If civilization continuity is exhausted while raid packets remain, the proportional survivors return through the existing aggregate-city raid-resolution authority.

## Why this is convergence rather than a new subsystem

No new city authority, raid economy, path model, combat resolver, casualty model, or host journal is introduced. The rung reuses:

- the existing hosted `city.provoke` event and hash-chained shared-world journal for the bound participant's canonical city mutation;
- `AggregateCity` / `WorldCityFabric` for browser city state, material-backed dispatch, and raid return/loss accounting;
- `WorldPressureDirector` for known-target pressure and bounded wave selection;
- `strategicTravelSeconds()` for finite world travel;
- `starterDropAnchor()` for the same deterministic planet coordinate used by the playable LOCAL seat;
- `LocalCombatGameplay` / formation combat for the player-facing fight;
- existing LOCAL casualty reconciliation, production/vehicle cleanup, structure siege, and civilization continuity for consequences.

Human and machine seats continue through the same admitted RTS action surface and participant action budget. 1–4 seats remain per-client access to one world model, not a global player cap.

## Truth boundary

The hosted part of this rung is intentionally narrow. For a bound seat, the host now durably journals and replay-applies the canonical `city.provoke` event before browser pressure follow-through. That does **not** prove the host observed or verified the convoy's physical arrival, selected-party travel history, cargo, or route state. The browser strategic journey remains client-observed evidence.

The browser city mirror is also not reconciled from the post-mutation host city snapshot. The host canonical city can therefore contain other durable world history that the browser mirror does not yet adopt. Host acceptance means the named canonical city was provoked by the bound participant; it does not mean the later browser city resource ledger is an authoritative copy of host state.

`WorldPressureDirector` target knowledge, raid expenditure/transit, aggregate-to-LOCAL mapping, LOCAL combat, casualties, civilization death, and browser raid resolution remain browser-local and are not host-replay-authoritative. The adapter is bounded deterministic gameplay compression, not a validated military-scale equivalence. The existing LOCAL defeat → explicit durable host close/score bridge still correlates a client-observed terminal state; the combat cause itself is not yet host-grounded.

This rung makes no claim about production hosting, concurrent multi-host scale, secure networking, final balance, final visuals, target-device performance, or bespoke character/vehicle/building animation.

## Next convergence seam

The next non-animation authority seam is to use the newly host-grounded canonical city event as provenance for the already-visible pressure/combat consequence without duplicating the LOCAL simulation. The smallest useful next proof should either derive/reconcile the minimum deterministic raid inputs from host canonical city state or admit a provenance-bearing raid/contact outcome that the host can replay-verify. Combat-caused civilization death should not be treated as host-grounded until that bridge exists.

A separate useful gameplay seam remains deterministic world-event presence/claim/reward integration; routing toward the nearest transport landmark is visible, but exact event participation and settlement are still unpromoted.
